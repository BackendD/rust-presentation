الگوهای طراحی در زبان Rust (بازنگری ۲۰۲۶)
بر اساس کتاب Design Patterns and Best Practices in Rust (2026)، الگوهای سنتی شی‌گرایی (GoF) مستقیماً به Rust ترجمه نمی‌شوند؛ بلکه سیستم مالکیت، سیستم تایپ غنی و تفکر اصیل Rust (Idiomatic) نحوه بازطراحی آنها را بازتعریف می‌کنند.

🚫 الگوهای ضدطراحی (Anti-Patterns):

  • تلاش برای تقلید کلاس و وراثت با Deref یا Traitهای توخالی
  • فرار از مالکیت با زدن چکش clone() بر همه چیز
  • سوءاستفاده از Rc<RefCell<T>> و شکستن قوانین کامپایلر
  • مبارزه با Borrow Checker و پناه بردن به unsafe یا Global Mutables

✨ الگوهای اصیل و مدرن (Idiomatic Patterns):

  • Creational: سازنده مطمئن (Builder) و متدهای کارخانه‌ای ایمن
  • Type-Driven: الگوهای TypeState، NewType و Sealed Traits
  • Structural & Behavioral: Decorator، Strategy و Command با Trait و Closure
  • Architectural: جریان داده رو‌به‌پایین، کپسوله‌سازی جهش‌پذیری و RAII
مقدمه بخش الگوهای طراحی: معرفی تغییر پارادایم از شی‌گرایی کلاسیک به تفکر نوع‌محور و اصیل در زبان راست.
الگوهای ضدطراحی (Anti-Patterns) در Rust
بزرگ‌ترین مانع یادگیری و نوشتن کد باکیفیت در Rust، «تلاش برای نوشتن جاوا یا ++C در قالب سینتکس راست» است. این مسیر به مبارزه مداوم با کامپایلر می‌انجامد.
ضدالگو (Anti-Pattern) انگیزه اولیه برنامه‌نویس پیامد و هزینه در Rust رویکرد اصیل جایگزین (Idiomatic)
وراثت مصنوعی با Deref دسترسی خودکار به متدهای ساختار داخلی ابهام در API، شکست کپسوله‌سازی، رفتارهای غافلگیرکننده ترکیب صریح (Composition) یا Delegation Trait
سوءاستفاده از Traitها ساختن سلسله‌مراتب کلاس‌های پایه و فرزند پیچیدگی بیهوده، محدودیت در object safety و Box<dyn> جداسازی رفتارها به تریت‌های کوچک و تک‌منظوره
چکش Clone فرار فوری از خطاهای Borrow Checker افت شدید کارایی و تخصیص‌های مکرر حافظه هیپ قرض‌گیری صحیح (&)، انتقال مالکیت یا اشتراک با Arc
سوءاستفاده از Rc/RefCell ایجاد گراف‌های پیچیده دوطرفه شی‌گرا انتقال خطای کامپایل به Panic در زمان اجرا (Runtime Crash) جریان داده یک‌طرفه (Data flows downward)
بررسی اجمالی چهار دسته اصلی خطاهای طراحی رایج در هنگام مهاجرت از زبان‌های شی‌گرا به راست.
چرا Rust زبان شی‌گرا به معنای سنتی نیست؟
در زبان‌های شی‌گرا کلاس هم داده (State) و هم رفتار (Behavior) و هم سلسله‌مراتب وراثت را ادغام می‌کند. اما در راست داده و رفتار کاملاً مستقل هستند.

❌ تلقی شی‌گرای اشتباه:

  • دیدن struct به‌عنوان یک کلاس حاوی فیلدهای خصوصی و عمومی
  • طراحی گراف‌های حلقوی از اشیا که اشاره‌گر مستقیم به هم دارند
  • تعریف اینترفیس‌های بزرگ با ده‌ها متد شبیه کلاس‌های انتزاعی
  • انتظار اینکه زیرکلاس بتواند رفتار والد را بازنویسی کند (Override)

✅ بینش Rust (طراحی اصیل):

  • انواع (Types) فقط داده خام هستند: چیدمان شفاف در حافظه بدون هزینه پنهان.
  • رفتار از طریق تریت‌ها پیاده می‌شود: تریت قرارداد قابلیت‌هاست نه هویت داده.
  • چندریختی ایستا (Static Polymorphism): مونو‌مورفایز شدن جنریک‌ها با کارایی صفر-هزینه.
  • تک‌مالکیتی (Single Ownership): مرزهای مشخص تغییرپذیری و طول‌عمرها.
قانون طلایی فصل دوم کتاب: «انواع شیء نیستند؛ تلاش برای تبدیل struct به شیء شی‌گرا، شما را رو در روی Borrow Checker قرار می‌دهد!»
بررسی تفکیک داده و رفتار در راست، رد ادغام کلاس‌محور و تشریح برتری مدل ترکیبی نسبت به مدل وراثتی سنتی.
ضدالگو: سوءاستفاده از Traitها مانند وراثت کلاس
وقتی برنامه‌نویسان تازه‌کار می‌خواهند درخت وراثت کلاس ایجاد کنند، شروع به ارث‌بری تریت از تریت با صدها متد و تبدیل اجباری به Box<dyn Trait> می‌کنند! 
// ❌ ضدالگو: تلاش برای شبیه‌سازی درخت وراثت کلاس با تریت‌های چندلایه
trait Operand { fn evaluate(&self) -> f64; }
trait Operator {
    fn precedence(&self) -> u8;
    fn push_operand(&mut self, op: Box);
}
trait BinaryOperator: Operator { /* متدهای اضافی شبیه کلاس فرزند */ }

// ✅ راه‌حل اصیل Rust: استفاده از الگوی داده‌محور با Enum
enum Expression {
    Number(f64),
    Binary { op: BinaryOp, left: Box, right: Box },
    Variable(String),
}

impl Expression {
    fn evaluate(&self, vars: &HashMap) -> Result {
        match self {
            Self::Number(n) => Ok(*n),
            Self::Variable(v) => vars.get(v).copied().ok_or_else(|| format!("متغیر {v} یافت نشد")),
            Self::Binary { op, left, right } => {
                let l = left.evaluate(vars)?;
                let r = right.evaluate(vars)?;
                op.apply(l, r)
            }
        }
    }
}
چگونه استفاده نابجا از Traitها برای شبیه‌سازی کلاس‌های انتزاعی به سردرگمی منجر می‌شود و چرا Enumها جایگزین مناسب‌تری برای دامنه‌های بسته هستند.
ضدالگو: پیاده‌سازی Deref برای شبیه‌سازی وراثت
Deref Polymorphism: تریت Deref فقط و فقط برای اشاره‌گرهای هوشمند (Smart Pointers) است؛ نه میانبری برای دسترسی رایگان به فیلدهای یک Struct درونی! 
// ❌ ضدالگو: استفاده از Deref برای به ارث بردن فیلدها و متدهای Base
struct BaseWidget { width: u32, height: u32 }
struct Button { base: BaseWidget, label: String }

impl std::ops::Deref for Button {
    type Target = BaseWidget;
    fn deref(&self) -> &Self::Target { &self.base } // ❌ شکستن معناشناسی Rust!
}

// ✅ راه‌حل اصیل: ترکیب صریح (Composition) یا پیاده‌سازی تریت واسط
trait Widget {
    fn dimensions(&self) -> (u32, u32);
}

struct ModernButton {
    base: BaseWidget,
    label: String,
}

impl Widget for ModernButton {
    fn dimensions(&self) -> (u32, u32) { (self.base.width, self.base.height) }
}
impl ModernButton {
    pub fn base(&self) -> &BaseWidget { &self.base } // دسترسی صریح و شفاف
}
چرا Deref Coercion نباید برای شبیه‌سازی وراثت فیلدها استفاده شود؛ خطرات نقض کپسوله‌سازی و تداخل متدها در آینده.
ضدالگو: جنریک‌های لجام‌گسیخته به جای کلاس‌ها
جنریک‌ها در Rust برای چندریختی ایستا (Compile-time Monomorphization) ساخته شده‌اند؛ افزودن پارامترهای بی‌پایان به Struct تنها برای تعمیم کاذب، کد را ناخوانا و زمان کامپایل را منفجر می‌کند. 
// ❌ ضدالگو: تورم پارامترهای تایپ جنریک برای پوشش هر حالت ممکن
struct Engine {
    fuel: Fuel, ignition: Ignition, cooling: Cooling,
    exhaust: Exhaust, transmission: Transmission,
}

// ✅ راه‌حل اصیل: پنهان‌سازی جزئیات در ماژول و استفاده از تریت‌های مهارشده
pub trait FuelSystem {
    fn inject_fuel(&mut self, amount: f32) -> Result<(), EngineError>;
}

pub struct EngineConfig {
    pub fuel: Box,
    pub transmission: TransmissionType, // Enum به‌جای جنریک بیهوده
}

pub struct Engine {
    config: EngineConfig,
    state: EngineState,
}
// به توازن میان Static Dispatch (سرعت بالا) و Dynamic Dispatch (سادگی API) دقت کنید!
مدیریت پیچیدگی پارامترهای جنریک، پرهیز از انفجار نوع در کد و درک توازن میان dispatch ایستا و پویا.
ضدالگو: کاربرد نادرست Enums و Enumهای عظیم
با اینکه enum در Rust فوق‌العاده قدرتمند است، اما قرار دادن واریانت‌های کاملاً ناهمگن و بزرگ در یک Enum واحد، باعث اتلاف حافظه و شکست توسعه‌پذیری (Open/Closed Principle) می‌شود. 
// ❌ ضدالگو: یک Enum غول‌آسا که تمام عملیات و ساختارهای ناهمگون را می‌بلعد
enum BadCalculatorCommand {
    Add(f64),
    Subtract(f64),
    PlotComplexGraph(Vec, Vec, [u8; 4096]), // حجم کل Enum به اندازه بزرگترین عضو می‌شود!
}

// ✅ رویکرد اصیل ۱: کوچک‌سازی سایز واریانت با Box
enum OptimizedCommand {
    Add(f64),
    Subtract(f64),
    PlotComplexGraph(Box), // اندازه حافظه در پشته یکسان و کوچک می‌ماند
}

// ✅ رویکرد اصیل ۲: وقتی دامنه دستورات باز و توسعه‌پذیر توسط کاربر است -> الگوی Trait Command
pub trait CalculatorCommand {
    fn execute(&mut self, calc: &mut Calculator) -> Result;
    fn undo(&mut self, calc: &mut Calculator) -> Result<(), String>;
}
تحلیل اثر حافظه‌ای واریانت‌های بزرگ در Enum، چرایی استفاده از Box و زمان مهاجرت از Enum به تریت برای توسعه‌پذیری باز.
ضدالگو: فرار از دغدغه‌های سیستم مالکیت (Ownership)
سیستم مالکیت Rust مانعی برای عبور نیست، بلکه یک «مشاور رایگان معماری نرم‌افزار» است که مرزهای اشتراک داده، چرخه حیات و اثرات جانبی (Side Effects) را شفاف می‌کند.
فرار از مالکیت: برنامه‌نویس وقتی با خطای lifetime یا borrow مواجه می‌شود، ساختار خود را با رفرنس‌های چرخه‌ای، متغیرهای عمومی با Mutex یا پوینترهای ناامن پر می‌کند؛ این امر به بن‌بست معماری می‌انجامد.
پذیرش مالکیت: بازآرایی ساختار به نحوی که هر موجودیت یک مالک منفرد و شفاف داشته باشد و داده‌ها رو به پایین جریان یابند (Downward Data Flow). 
// تفکر اصیل: مالکیت منبع، طول عمر آن را تضمین می‌کند
struct SessionManager {
    sessions: HashMap, // مالک حقیقی سشن‌ها
}
impl SessionManager {
    // فقط رفرنس کوتاه‌مدت یا نمایه امانت داده می‌شود، نه مالکیت اشتراکی نامحدود
    pub fn get_session(&self, id: &SessionId) -> Option<&UserSession> {
        self.sessions.get(id)
    }
}
سیستم مالکیت راست به عنوان ابزار طراحی؛ چگونگی شفاف‌سازی مرزهای داده‌ها و چرخه حیات منابع در معماری سیستم.
ضدالگو: چکش Clone — کپی‌کردن همه‌چیز!
The Clone Hammer: حل خطاهای کامپایلر با افزودن .clone() در همه جا، بدهی فنی سنگین و افت کارایی شدیدی (پنهان در تخصیص‌های مکرر Heap) تولید می‌کند. 
// ❌ ضدالگو: کلون کردن تمام پیام‌ها و ساختارها برای فرار از borrow checker
fn process_events(events: Vec, filter: &str) -> Vec {
    let mut matched = Vec::new();
    for ev in events.clone() { // ❌ کلون کردن بردار کامل و رشته‌ها!
        if ev.message.clone().contains(filter) { // ❌ کلون رشته فقط برای جستجو!
            matched.push(ev.clone());
        }
    }
    matched
}

// ✅ راه‌حل اصیل: استفاده از رفرنس و امانت‌گرفتن بدون هزینه (Zero-Cost Borrowing)
fn process_events_idiomatic<'a>(events: &'a [EventLog], filter: &str) -> Vec<&'a EventLog> {
    events
        .iter()
        .filter(|ev| ev.message.contains(filter)) // رفرنس خواندنی بدون هیچ کپی
        .collect() // فقط اشاره‌گرها جمع‌آوری می‌شوند، بدون کلون کردن بدنه رویدادها!
}
نقد الگوی ضدطراحی چکش کلون؛ بررسی تفاوت کارایی میان ایجاد کپی‌های عمیق در هیپ و قرض‌گیری خواندنی با طول‌عمر مشترک.
ضدالگو: سوءاستفاده از Rc و RefCell
تبدیل تمام انواع به Rc<RefCell<T>> به منظور شبیه‌سازی مدل حافظه جاوا/پایتون، بررسی‌های ایمنی زمان کامپایل را خاموش کرده و منجر به Panic در زمان اجرا و نشت حافظه (Memory Leaks via Reference Cycles) می‌شود. 
// ❌ ضدالگو: ایجاد رفرنس‌های دوطرفه و پیچیده شبیه آبجکت‌های شی‌گرا
struct BadNode {
    parent: Option>>,
    children: Vec>>, // ⚠️ خطر چرخه ارجاع و نشت دائمی حافظه!
}

// ✅ راه‌حل اصیل ۱: استفاده از Rc::downgrade و Weak برای فرزند به والد
struct TreeChild {
    parent: std::rc::Weak>, // عدم جلوگیری از آزادسازی حافظه
}

// ✅ راه‌حل اصیل ۲ (رویکرد مدرن در Rust): آرنا / شناسه برداری (SlotMap یا Index-based)
struct ArenaTree {
    nodes: Vec, // یک مالک واحد برای همه نودها
}
struct NodeId(usize);
struct NodeData {
    parent: Option,
    children: Vec,
} // صددرصد ایمن، بدون نیاز به RefCell و بدون کوچکترین خطر Memory Leak!
بررسی خطرات چرخه ارجاعی با Rc/RefCell و معرفی الگوهای جایگزین اصیل مانند Weak pointers و Arena Allocations بر پایه اندیس‌ها.
مبارزه با Borrow Checker، فرار به Unsafe و Globals
وقتی طراحی سیستم نادرست باشد، برخی توسعه‌دهندگان به static mut یا بلوک‌های unsafe پناه می‌برند؛ کتاب نشان می‌دهد که این مسیر خطرناک‌ترین تله در Rust است.
خطرات میانبرهای نامطمئن:
  • static mut ذاتاً ناامن است و در نسخه‌های جدید Rust به‌طور جدی منع شده است.
  • استفاده از unsafe برای دور زدن رفرنس‌ها، گارانتی ایمنی حافظه را بی‌اثر و Undefined Behavior ایجاد می‌کند.
  • مشکل از کامپایلر نیست؛ معماری داده نیاز به بازطراحی دارد!
// ✅ راه‌حل ایمن برای متغیرهای پیکربندی و وضعیت گلوبال:
use std::sync::OnceLock;

// مقداردهی تنبل و ایمن در سطح برنامه
static CONFIG: OnceLock = OnceLock::new();

pub fn get_config() -> &'static AppConfig {
    CONFIG.get_or_init(|| AppConfig::load_from_env())
}
// بدون نیاز به unsafe، بدون race condition و کاملاً سازگار با نخ‌ها (Thread-Safe)
بررسی فصل چهارم کتاب: پرهیز از تله unsafe و وضعیت‌های متغیر سراسری، و جایگزینی آن با ساختارهای مدرنی مثل OnceLock.
الگوهای سازنده — تفسیری نو در زبان Rust
در زبان‌های شی‌گرا الگوهای سازنده برای پوشش کاستی‌های Constructorها و وراثت به وجود آمدند. در Rust با وجود Default، الگوهای ساخت با کنترل مالکیت (Ownership Transfer) غنی‌تر می‌شوند.
الگو رویکرد سنتی شی‌گرایی معادل و نحوه تحقق در Rust مزیت اصیل در Rust
Factory Method زیرکلاس‌ها متد ساخت شیء را override می‌کنند توابع ایستا مانند Type::new() یا From / Into ساده، صریح و بدون نیاز به سربار وراثت و جدول مجازی
Abstract Factory اینترفیس‌های درهم‌تنیده برای تولید خانواده اشیا تریت‌های کارخانه با Associated Types یا Generics بررسی سازگاری خانواده نوع در زمان کامپایل (Zero Cost)
Builder کلاس‌های جداگانه با متدهای زنجیره‌ای با ارجاع الگوی Consuming Builder یا State-Machine Builder مصرف مالکیت ساختار ناقص و تولید نوع نهایی تغییرناپذیر
Prototype متد clone() بر روی آبجکت‌های پویا تریت استاندارد Clone با Derive خودکار کپی عمیق صریح با تضمین عدم مداخله پنهان در اشاره‌گرها
معرفی الگوهای ساخت در راست و مقایسه عملکرد آن‌ها با الگوهای کلاسیک شی‌گرایی.
الگوی سازنده اصیل: Consuming Builder
در Rust متدهای Builder معمولاً mut self را مصرف می‌کنند (Move)؛ این امر از ایجاد کپی غیرضروری جلوگیری کرده و شیء نیمه‌ساخته را پس از build() غیرقابل‌استفاده می‌سازد. 
#[derive(Debug)]
pub struct ServerConfig {
    host: String,
    port: u16,
    max_connections: usize,
    tls_enabled: bool,
}

#[derive(Default)]
pub struct ServerConfigBuilder {
    host: Option,
    port: Option,
    max_connections: Option,
    tls_enabled: bool,
}

impl ServerConfigBuilder {
    pub fn new() -> Self { Self::default() }
    pub fn host(mut self, host: impl Into) -> Self {
        self.host = Some(host.into());
        self
    }
    pub fn port(mut self, port: u16) -> Self { self.port = Some(port); self }
    pub fn enable_tls(mut self) -> Self { self.tls_enabled = true; self }

    pub fn build(self) -> Result {
        Ok(ServerConfig {
            host: self.host.ok_or("آدرس میزبان الزامی است")?,
            port: self.port.unwrap_or(8080),
            max_connections: self.max_connections.unwrap_or(1024),
            tls_enabled: self.tls_enabled,
        })
    }
}
بررسی پیاده‌سازی گام‌به‌گام الگوی Builder به شکل مصرف‌کننده (Consuming) و ولیدیشن پارامترها در متد build.
کارخانه و تبدیل‌ها با تریت‌های استاندارد
به‌جای ایجاد کلاس‌های پیچیده Factory، زبان Rust از قراردادهای نام‌گذاری اصیل و تریت‌های توکار From / TryFrom برای ساخت و تبدیل شی‌ءها استفاده می‌کند. 
// الگوهای مرسوم نام‌گذاری کارخانه‌ای در Rust:
// 1. `new(...)` -> سازنده استاندارد پیش‌فرض
// 2. `with_capacity(n)` -> سازنده با پیکربندی اولیه بهینه
// 3. `from_str(...)` -> تبدیل مبتنی بر تحلیل ورودی متنی

#[derive(Debug, PartialEq)]
pub struct Port(u16);

// پیاده‌سازی تریت استاندارد TryFrom به عنوان Factory تبدیل ایمن
impl TryFrom for Port {
    type Error = &'static str;
    fn try_from(value: u32) -> Result {
        if value > 0 && value <= 65535 {
            Ok(Port(value as u16))
        } else {
            Err("شماره پورت نامعتبر است (باید بین ۱ تا ۶۵۵۳۵ باشد)")
        }
    }
}

fn main() {
    let p = Port::try_from(443).expect("پورت معتبر");
    // تریت معکوس `TryInto` نیز به‌طور خودکار فعال است:
    let p2: Result = 8080u32.try_into();
}
استفاده از تریت‌های هسته راست برای ساخت انواع معتبر؛ بهره‌گیری از From و TryFrom به‌جای فکتوری‌های زائد شی‌گرا.
الگوهای ساختاری — اتصال و ترکیب کامپوننت‌ها
الگوهای ساختاری در Rust به کمک تریت‌ها و سیستم ماژولار بدون نیاز به وراثت، ترکیب‌پذیری فوق‌العاده بالایی با عملکرد صفر-هزینه فراهم می‌سازند.
  • 🛡️ Newtype: بسته‌بندی یک تایپ موجود در یک Struct تک‌فیلدی برای تفکیک معنایی بدون Overhead در حافظه.
  • 🎨 Decorator: تزئین رفتار یک اینترفیس (تریت) با یک پوشاننده دیگر بر روی همان تریت.
  • 🔌 Adapter: منطبق‌سازی یک کتابخانه یا نوع ناسازگار با استفاده از تریت‌های مشترک.
  • 🏛️ Facade: سازمان‌دهی ماژول‌ها و صدور مجدد (pub use) توابع ساده‌سازی‌شده برای مصرف‌کننده خارجی.
  • 🌲 Composite: ایجاد ساختارهای درختی یا گره‌های مرکب از طریق ترکیب بازگشتی enum یا Box<dyn Trait>.
مرور الگوهای ساختاری فصل ششم کتاب راست: Adapter، Decorator، Facade و Newtype.
الگوی Newtype — ایمنی نوع بدون هزینه حافظه
ویژگی #[repr(transparent)] تضمین می‌کند که در سطح ماشین و حافظه، هیچ تفاوت و سرباری بین نوع جدید و نوع درونی وجود ندارد. 
// جلوگیری قطعی از اشتباه در مقادیر هم‌جنس (مانند شناسه‌های عددی یا واحدها)
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub struct UserId(pub u64);

#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub struct OrderId(pub u64);

fn cancel_order(user: UserId, order: OrderId) {
    println!("لغو سفارش {} متعلق به کاربر {}", order.0, user.0);
}

fn main() {
    let user = UserId(1001);
    let order = OrderId(5005);

    // cancel_order(order, user); // ❌ خطای زمان کامپایل! ترتیب اشتباه غیرممکن است
    cancel_order(user, order);    // ✅ کاملاً امن و واضح

    // همچنین دور زدن قانون یتیم (Orphan Rule) برای پیاده‌سازی تریت خارجی روی نوع خارجی:
    struct CustomVec(Vec);
    impl std::fmt::Display for CustomVec {
        fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
            write!(f, "[{}]", self.0.join(", "))
        }
    }
}
مزایای چندگانه Newtype: تضمین ایمنی تایپ بدون هزینه ران‌تایم، حل محدودیت Orphan Rule و تعریف رابط مشخص.
الگوی Decorator اصیل در Rust
تزئین پویا یا ایستا: می‌توان دکوراتور را با جنریک‌ها به صورت ایستا (Inlined) یا با Box<dyn Trait> به صورت پویا زنجیره کرد. 
pub trait Evaluator {
    fn eval(&self, expr: &str) -> Result;
}

pub struct BasicCalculator;
impl Evaluator for BasicCalculator {
    fn eval(&self, expr: &str) -> Result {
        // محاسبه فرضی
        Ok(42.0)
    }
}

// دکوراتور ثبت لاگ (Logging Decorator) به کمک جنریک و کامپایل ایستا (Zero Cost)
pub struct LoggingEvaluator {
    inner: E,
}
impl LoggingEvaluator {
    pub fn new(inner: E) -> Self { Self { inner } }
}
impl Evaluator for LoggingEvaluator {
    fn eval(&self, expr: &str) -> Result {
        println!("🚀 در حال محاسبه عبارت: {expr}");
        let res = self.inner.eval(expr);
        println!("🏁 نتیجه به دست آمده: {res:?}");
        res
    }
}
پیاده‌سازی Decorator در راست به شکل ایستا با جنریک‌ها بدون سربار vtable و قابلیت ترکیب تودرتو.
الگوهای رفتاری — هماهنگی عملیات و حالت
در Rust الگوهای رفتاری به دلیل انطباق کامل با کلوژرها، تریت‌های Fn و تطبیق الگو (Pattern Matching) بسیار موجزتر از پیاده‌سازی‌های کلاسیک هستند.

🎯 الگوی استراتژی (Strategy):

می‌تواند از طریق یک تریت اختصاصی، و یا به سادگی از طریق ارسال یک Closure با امضای impl Fn(...) به تابع پیاده شود؛ بدون تعریف کلاس‌های اضافی!

📜 الگوی دستور (Command):

کپسوله‌سازی یک عمل به همراه داده‌های لازم برای اجرای آن و پیاده‌سازی قابلیت Undo/Redo با مدیریت دقیق مالکیت پشته تاریخچه.

👁️ الگوی ناظر (Observer):

به دلیل قوانین قرض‌گیری و جلوگیری از ارجاعات چرخه‌ای، با کانال‌های ارتباطی (mpsc::channel) یا لیست کالبک‌های تریت به شکلی امن بازنویسی می‌شود.

🔄 الگوی پیمایشگر (Iterator):

شهروند درجه یک در زبان Rust؛ با متد next() و ده‌ها مبدل تنبل (Lazy Adapters) با کارایی معادل حلقه‌های دستی C.

معرفی الگوهای رفتاری مطرح در فصول ۷ و ۸ کتاب (Command، Strategy، Observer، Iterator).
الگوی Strategy — با تریت‌ها و بستارها (Closures)
انعطاف دوگانه در Rust: استفاده از تریت برای استراتژی‌های پیچیده سازمانی، یا کلوژرها برای پیاده‌سازی‌های جمع‌وجور و سبک. 
// رویکرد اول: استراتژی کلاسیک با تریت (Dynamic / Boxed Strategy)
pub trait CompressionStrategy {
    fn compress(&self, data: &[u8]) -> Vec;
}

// رویکرد دوم (رویکرد فوق‌العاده شیک با Closure در زبان Rust):
pub struct DataProcessor
where
    F: Fn(&[u8]) -> Vec,
{
    strategy: F,
}

impl DataProcessor
where
    F: Fn(&[u8]) -> Vec,
{
    pub fn new(strategy: F) -> Self { Self { strategy } }
    pub fn process(&self, data: &[u8]) -> Vec {
        (self.strategy)(data)
    }
}

fn main() {
    // تزریق استراتژی در محل بدون نیاز به تعریف نوع و استراکت جدید!
    let gzip_processor = DataProcessor::new(|bytes| {
        println!("فشرده‌سازی با الگوریتم دلخواه...");
        bytes.to_vec()
    });
    let output = gzip_processor.process(b"سلام دنیا");
}
پیاده‌سازی استراتژی با کلوژرها در راست؛ حذف کد زائد (Boilerplate) کلاس‌ها به نفع چندریختی مرتبه بالا.
الگوی Command با قابلیت بازگشت (Undo / Redo)
دستورات حالت قبلی را در درون خود ذخیره می‌کنند و تاریخچه از طریق یک بردار از Box<dyn Command> مدیریت می‌شود. 
pub trait Command {
    fn execute(&mut self, state: &mut f64) -> Result<(), &'static str>;
    fn undo(&mut self, state: &mut f64) -> Result<(), &'static str>;
}

pub struct AddCommand {
    amount: f64,
}
impl AddCommand {
    pub fn new(amount: f64) -> Self { Self { amount } }
}
impl Command for AddCommand {
    fn execute(&mut self, state: &mut f64) -> Result<(), &'static str> {
        *state += self.amount;
        Ok(())
    }
    fn undo(&mut self, state: &mut f64) -> Result<(), &'static str> {
        *state -= self.amount; // برگرداندن تغییرات
        Ok(())
    }
}

pub struct CommandManager {
    history: Vec>,
}
impl CommandManager {
    pub fn run(&mut self, mut cmd: Box, state: &mut f64) {
        if cmd.execute(state).is_ok() {
            self.history.push(cmd);
        }
    }
}
الگوی فرمان در راست؛ نگهداری پشته تاریخچه دستورات و مدیریت دقیق مالکیت آبجکت‌های تریت در وکتور.
الگوهای معماری در سیستم‌های کلان Rust (Samsa)
در فصل نهم کتاب بر اساس پیاده‌سازی میکروسرویس Samsa (سامانه پیام‌رسان توزیع‌شده مشابه کافکا)، چهار اصل معماری کلیدی معرفی می‌شود:
۱. جریان داده رو‌به‌پایین (Data Flows Downward): داده‌ها از بالا به پایین منتقل می‌شوند (تولیدکننده -> بروکر -> مصرف‌کننده). هیچ رفرنس بالادستی وجود ندارد و خطر نشت یا چرخه‌های نامعتبر صفر است.
۲. مهار جهش‌پذیری (Mutability Stays Contained): پیام‌ها ذاتا تغییرناپذیرند. تغییرات فقط در هسته بروکر کنترل می‌شود و به بیرون سرایت نمی‌کند.
۳. ماژول‌ها به‌مثابه واسط‌ها (Modules as Interfaces): ماژول‌ها مرز کپسوله‌سازی هستند. فقط ساختارهای ضروری با pub آشکار می‌شوند.
۴. ساختارهای سبک‌بال (Pack Lightly & Zero-Copy): بهره‌گیری از اسلایس‌ها و نماهای بدون کپی (Zero-Copy Views) به‌جای بسته‌بندی داده‌های سنگین تکراری در حافظه.
اصول معماری سامانه Samsa در کتاب: جهت جریان داده، محدود کردن mutability و طراحی کم‌مصرف حافظه.
الگوی معماری RAII و پاکسازی خودکار منابع
Resource Acquisition Is Initialization: گارانتی قطعی آزادسازی منابع (سوکت، فایل، قفل، حافظه گرافیک) در زمان خروج از اسکوپ، بدون نیاز به بلوک‌های دست‌وپاگیر try-finally. 
use std::fs::File;
use std::io::Write;

pub struct TempDirectory {
    path: std::path::PathBuf,
}

impl TempDirectory {
    pub fn new(name: &str) -> std::io::Result {
        let path = std::env::temp_dir().join(name);
        std::fs::create_dir_all(&path)?;
        Ok(Self { path })
    }
}

// پیاده‌سازی Drop ضامن حذف حتمی دایرکتوری در پایان عمر شیء است
impl Drop for TempDirectory {
    fn drop(&mut self) {
        if self.path.exists() {
            let _ = std::fs::remove_dir_all(&self.path);
            println!("🧹 دایرکتوری موقت با موفقیت پاکسازی شد: {:?}", self.path);
        }
    }
}

    // مفسر به صورت تضمین‌شده متد drop() را صدا زده و دایرکتوری پاک می‌شود!

الگوی انقلابی TypeState — مدیریت وضعیت در کامپایل
الگوی TypeState وضعیت شیء را در نوع جنریک آن کدگذاری می‌کند؛ متدهایی که در یک وضعیت نامعتبر هستند اصلاً در زمان کامپایل وجود ندارند! 
use std::marker::PhantomData;

// نشانگرهای وضعیت (Zero-Sized Types بدون هزینه حافظه)
pub struct Disconnected;
pub struct Connected;

pub struct Consumer {
    topic: String,
    _state: PhantomData,
}

impl Consumer {
    pub fn new(topic: impl Into) -> Self {
        Self { topic: topic.into(), _state: PhantomData }
    }
    // تغییر وضعیت با مصرف شیء قبلی و بازگرداندن نوع در وضعیت جدید
    pub fn connect(self) -> Consumer {
        println!("اتصال به بروکر برقرار شد.");
        Consumer { topic: self.topic, _state: PhantomData }
    }
}

impl Consumer {
    pub fn poll_message(&self) -> Option {
        Some(format!("پیام از موضوع {}", self.topic))
    }
}

fn main() {
    let consumer = Consumer::new("orders");
    // consumer.poll_message(); // ❌ خطای کامپایلر! در حالت Disconnected متد وجود ندارد!
    let active = consumer.connect();
    println!("{:?}", active.poll_message()); // ✅ معتبر و مطمئن در زمان کامپایل!
}
الگوی شگفت‌انگیز TypeState از فصل ۱۰ کتاب: انتقال چک‌های حالت ران‌تایم به خطا در زمان کامپایل با ZST و PhantomData.
اصل «Parse, Don't Validate» و Sealed Traits
به جای بررسی تکراری شرط‌ها در سراسر برنامه (Validate)، داده را هنگام ورود به یک نوع تضمین‌شده تبدیل کنید (Parse) تا سیستم تایپ ضامن درستی آن باشد.

✅ ساخت انواع خود-معتبرساز:

#[derive(Debug, Clone, Copy)]
pub struct PositiveU32(u32);

impl PositiveU32 {
    pub fn parse(val: u32) -> Result {
        if val > 0 { Ok(Self(val)) }
        else { Err("باید بزرگتر از صفر باشد") }
    }
    pub fn get(self) -> u32 { self.0 }
}
// هر تابعی که PositiveU32 می‌گیرد، 
// نیازی به بررسی مجدد ندارد!

🔒 تریت‌های مهروموم‌شده (Sealed Traits):

// جلوگیری از پیاده‌سازی تریت در کریت‌های دیگر
mod private {
    pub trait Sealed {}
}

pub trait SafeSchema: private::Sealed {
    fn serialize(&self) -> Vec;
}

pub struct CoreSchema;
impl private::Sealed for CoreSchema {}
impl SafeSchema for CoreSchema {
    fn serialize(&self) -> Vec { vec![] }
}
// کنترل کامل و حفظ سازگاری کریت در ارتقاها!
معرفی الگوهای پیشرفته سیستم نوع در راست: Parse Don't Validate بر اساس مقاله الکسیس کینگ و Sealed Traits برای کنترل پیاده‌سازی‌ها.
الگوهای تابعی — خطوط لوله، بستارها و ایتراتورها
خط لوله توابع (Pipelines) و ایتراتورهای ارزیابی‌تنبل (Lazy) به کامپایلر اجازه می‌دهند عملیات را یکپارچه کرده و به کدی بهینه و عاری از تخصیص حافظه تبدیل کند. 
#[derive(Debug)]
struct Transaction { id: u64, amount: f64, verified: bool }

fn main() {
    let txs = vec![
        Transaction { id: 1, amount: 120.0, verified: true },
        Transaction { id: 2, amount: -50.0, verified: false },
        Transaction { id: 3, amount: 300.0, verified: true },
    ];

    // خط لوله تابعی (Pipeline) — بدون نیاز به ایجاد وکتورهای موقت:
    let total_verified: f64 = txs.iter()
        .filter(|t| t.verified && t.amount > 0.0) // فیلتر تراکنش‌های مثبت معتبر
        .map(|t| t.amount * 1.09)                 // محاسبه با احتساب مالیات
        .fold(0.0, |acc, val| acc + val);          // تجمیع مقادیر

    println!("مجموع پرداختی: {:.2}", total_verified);

    // تلفیق با Pattern Matching و if let
    if let Some(first_large) = txs.iter().find(|t| t.amount >= 200.0) {
        println!("تراکنش عمده کشف شد: شماره {}", first_large.id);
    }
}
سبک تابعی در راست: خطوط پردازش داده با Iterator و ترکیب Closureها، دستیابی به سادگی و سرعت بیشینه بدون تخصیص زائد.
جمع‌بندی: از کدنویسی تا تفکر در Rust (Think in Rust)
فصل سیزدهم کتاب نتیجه می‌گیرد: تسلط بر Rust زمانی رخ می‌دهد که دیگر تلاش نکنید الگوهای زبان‌های قبلی خود را پیاده کنید، بلکه به زبان اجازه دهید شما را به سمت طراحی اصیل هدایت کند.

💡 اصول بنیادین تفکر در Rust:

  • مالکیت به‌مثابه فلسفه طراحی: ساختار داده‌ها را بر مبنای طول‌عمر و مالکان حقیقی مدل کنید.
  • ترکیب بر وراثت به شکلی طبیعی: تریت‌های کوچک، Structهای متمرکز و Enumهای گویای دامنه مسئله.
  • انتزاع‌های صفر-هزینه (Zero-Cost): کد تمیزتر مساوی با افت کارایی نیست؛ کامپایلر آن را بهینه می‌کند.

🎯 توسعه هدایت‌شده توسط کامپایلر (CDD):

  • Borrow Checker مشاور معماری شماست: هر خطای قرض‌گیری نشانه‌ای از یک ابهام بالقوه در مرزهای تغییرپذیری است.
  • صراحت (Explicitness): خطرات و مدیریت خطاها با Result / Option در امضای توابع فریاد زده می‌شوند.
  • تایپ‌ها ضامن امنیت هستند: با TypeState، وضعیت نامعتبر غیرقابل‌نمایندگی است.
«Make illegal states unrepresentable — با کمک سیستم تایپ، امکان ایجاد وضعیت نامعتبر در برنامه را در زمان کامپایل از بین ببرید!»
